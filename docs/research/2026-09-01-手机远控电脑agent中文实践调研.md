## 发现

### 一、完全同构方案（手机下发 → 电脑 AI 执行 → 进度推回手机）

**1. OpenClaw（原 Clawdbot）—— 最主流、完整度最高**
- 平台：GitHub（`openclaw/openclaw`，**388,488 stars**）
- URL：https://github.com/openclaw/openclaw
- 简介：开源 AI 个人助理，跑在自家机器上，通过你已在用的 IM（Telegram/WhatsApp/微信/飞书/钉钉等）控制本机 Claude Code/GPT 执行任务，结果/进度实时回传 IM。**原生支持 Telegram Bot**（正是目标架构备选链路）。
- 中文社区：https://open-claw.org.cn/ （DeepSeek-V3/Qwen 源码级支持、npmmirror 预配置、飞书/企业微信连接器开发中）
- 教程三源交叉验证：
  - eastondev《OpenClaw Telegram 集成教程》2026-02-05：https://eastondev.com/blog/zh/posts/ai/20260205-openclaw-telegram-integration/
  - 知乎《OpenClaw（原 Clawdbot）2.0 保姆级安装》2026-01-30：https://zhuanlan.zhihu.com/p/2000607262222336933
  - bnext《Claude Code Channels 4 步骤设定 Telegram 远端下指令》2026-04-06：https://www.bnext.com.tw/article/90462/claude-code-channels-openclaw
- 重合度：**完全同构**（IM 入口替代了「HTTP Shortcuts 发指令」这一步，其余链路一致）
- 可复用结论：手机=遥控器、电脑=常驻 gateway（`openclaw gateway` 或 Docker）、Telegram Bot 用 `dmPolicy: allowlist + allowFrom` 白名单防额度被盗刷。

**2. im-hub —— 通用「IM↔Agent」桥（含自定义 ACP agent，最贴近本架构）**
- 平台：GitHub（`ceociocto/im-hub`），MIT
- URL：https://github.com/ceociocto/im-hub ；npm：`im-hub`
- 简介：Universal messenger-to-agent bridge，连接 微信/飞书/Telegram → Claude Code/Codex/Copilot/OpenCode，**或任何自定义 agent（通过 ACP 协议，标准 HTTP endpoint）**。飞书走 **WebSocket 长连接，无需公网 IP/域名/ngrok**；还内置 Web Chat（浏览器直接聊，`localhost:3000`）。
- 前身：`ceociocto/opencode-remote-control`（已 DEPRECATED，迁移到 im-hub）
- 重合度：**完全同构**（若把「HTTP Shortcuts + FastAPI 路由服务」替换成 im-hub 的 ACP 自定义 agent，或直接接 OpenCode/Claude Code，链路直接打通）
- 可复用结论：`npm install -g im-hub` → `im-hub config feishu`（免公网回传）→ `im-hub config claude` → `im-hub start`；自定义 agent 用 `im-hub config agent` 填 HTTP endpoint + Bearer/API Key。

**3. agent-feishu-bridge —— 飞书桥（7 种 agent 后端，含 OpenCode/Claude/OpenClaw）**
- 平台：GitHub（`Jokerautowrite/agent-feishu-bridge`），猫哥工作室，custom license（个人学习/非商业内部工具免费）
- URL：https://github.com/Jokerautowrite/agent-feishu-bridge
- 简介：把本地 AI Agent 接入飞书/Lark，后端支持 Codex/OpenCode/Claude Code/Chuang/OpenClaw/Hermes/Grok。流式卡片、工具状态、审批、文件传输。**飞书官方长连接，不要求公网回调地址**。Windows 用当前用户启动项（等价 NSSM 场景）、Linux systemd user、macOS LaunchAgent 一键安装。
- 关键点：OpenCode 后端走 `opencode serve` + SDK/SSE；Claude 后端走 `claude -p --output-format stream-json`——**这正好是目标架构 PC 端「调用 CLI agent」的现成实现**。
- 重合度：**完全同构**（IM=飞书，agent 后端=OpenCode/Claude，Windows 后台常驻已内置）
- 可复用结论：一行安装 `irm .../install.ps1 | iex`；`/bind` 绑定项目、`/new` `/switch` 会话管理、`/approve` `/reject` 远程审批、`/send` 文件回传。

**4. DSH-Remote 生态 —— 「口袋里的 DSH」手机遥控器（Tailscale/LAN 直连）**

## 结论与置信度

### 核心结论

1. **「手机下发 → 电脑 AI 执行 → 进度推回手机」这条链路在中文社区已是成熟赛道，有大量「完全同构」的开源项目**，主流做法是「IM 机器人（Telegram/飞书/微信）当作手机遥控器」而非「HTTP Shortcuts 按钮」。置信度：**高**（OpenClaw 38.8 万 star、DSH 20.7 万 star、多个中文飞书/Telegram 桥交叉验证）。

2. **最贴近本架构的可照抄方案排序**：
   - 若接受「IM 代替 HTTP Shortcuts 发指令」→ **OpenClaw**（最成熟）、**im-hub**（含自定义 ACP agent，最灵活、MIT）、**agent-feishu-bridge**（飞书长连接免公网 + 7 后端，Windows 常驻内置）。
   - 若坚持「自建 CLI agent（opencode/claude -p）+ 自建路由」→ **im-hub 的 ACP 自定义 agent** 或 **opencode serve + opencode_android_client / message-bridge 插件**，再叠加 **eogee 的 ntfy 双向交互范式**。
   - 若 agent 换成 DeepSeek Harness → **DSH-Remote 生态**（Tailscale 直连 + Token 鉴权 + 断线自愈）。

3. **必须自己补写的部分**（见清单 B）主要集中在本架构「HTTP Shortcuts + FastAPI 路由 + ntfy 推回」这条**自建、非 IM 化**的独特组合上——社区里几乎没有人和你一样「不用 IM、纯 HTTP 按钮发指令」；但这三个组件各自都有现成实现，拼装成本低。

4. **关键风险点（两源以上交叉验证）**：① ntfy 国内安卓依赖 FCM，推送不稳（V2EX + CSDN 双源）；② Tailscale 免费版 3 台设备 + 国内需 DERP 中继 + 安卓杀后台（CSDN + linux.do + stonehoo 三源）；③ Claude Code 官方 Channels/Remote Control 强绑定 claude.ai 订阅登录，不适合「自建 CLI agent」路线。

### 置信度说明
- 高置信（≥2 独立源交叉验证）：OpenClaw 存在与 Telegram 原生支持、ntfy 国内 FCM 问题、Tailscale 免费额度/国内 DERP、OpenCode `serve` 模式、DSH-Remote 生态。
- 中置信（单源或宣传性内容，未逐一复现）：im-hub/agent-feishu-bridge 的「免公网 IP」实际效果、eogee 工具链的「安装一个包即可用」、HTTP Shortcuts 的认证细节。

## B. 必须自己补写的部分

1. **「HTTP Shortcuts 按钮 → 自建路由服务」这条非 IM 化入口**：社区现成方案几乎都走 IM 机器人，没有人用「纯 HTTP 按钮」作为发指令入口。需自己写 FastAPI/Node 路由服务，接收 HTTP Shortcuts 的 POST 并转发给 `opencode run` / `claude -p`（可参考 agent-feishu-bridge 的 `claude -p --output-format stream-json` 调用方式与 im-hub 的 ACP endpoint 规范）。
2. **进度回传的双向通道封装**：把 agent 的流式输出（stdout/SSE/stream-json）实时转发到 ntfy topic，并在需要确认时用 ntfy Action（按钮）回调。可借鉴 eogee 工具链的「ntfy 交互确认 + 远程续聊」设计，但其具体实现需自行落地。
3. **国内 ntfy 安卓推送可靠性**：FCM 被墙导致推送不稳，需自建 ntfy 后改用 WebSocket 长连接 + 客户端保活，或预置 Bark/PushDeer/Chanify 备选通道（需自己写多通道 fallback）。
4. **Windows 服务化 + 鉴权**：路由服务 + agent 进程用 NSSM 注册为 Windows 服务并加 Token/Basic Auth（opencode serve 已内置 Basic Auth，自建 FastAPI 需自行加鉴权），防止公网（即便走 Tailscale 也建议内网鉴权）。
5. **Tailscale 国内中继与设备配额**：自建 DERP 或选用国内 DERP 节点，管理 3 台免费设备配额（PC + 手机 + 备用）。
6. **opencode 插件生态的坑**：message-bridge 插件当前受 `fn3 is not a function`（opencode issue #7792）影响需走 dev 模式；注意版本适配。
