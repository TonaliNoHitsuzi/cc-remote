## 发现

### 关键背景：2025–2026 个人微信通道格局剧变

- **个人微信 hook/协议类开源项目大面积停更或删除**。WeChatFerry（`lich0821/WeChatFerry`）仓库已**归档（archived=true）**；Gewechat（`Devo919/Gewechat`）README 明确标注「**本项目已停止维护，仅作技术归档**」，并链接腾讯《针对违规获取及利用微信终端用户数据行为的打击公告》作为停更背景；ntchat（`smallevilbeast/ntchat`）原仓库已 **404 删除**。多个独立来源（CSDN 停更替代文章、凌霆贝社区、CowAgent issue #2568「暂时不要使用了，会引起风控」）交叉证实：**腾讯 2024–2025 加大了对微信外挂/逆向/违规获取用户数据的打击，个人号 hook 方案封号/风控风险显著上升**。
- **腾讯官方开辟了合规的个人微信通道**：`Tencent/openclaw-weixin`（OpenClaw 的官方微信渠道插件），基于 ClawBot iLink API，**扫码登录 + HTTP 长轮询（getUpdates）收发消息**，无需 Webhook、非逆向协议。这成为个人微信接入的新「正路」，AstrBot 等框架已跟进接入。
- 个人微信自动化项目的「老一代」（itchat、ntchat、wxhelper、WeChatFerry、Gewechat）→ 基本只能算历史资料，**不宜再作为新项目技术选型**；「新一代」是官方 openclaw-weixin + 合规的自建应用/公众号路线。

#### 1.3 企业微信自建应用 API（官方合规，推荐）

- **接入方式**：在企业微信管理后台创建「自建应用」→ 配置回调 URL + Token + EncodingAESKey → 服务器接收 GET（验证）/POST（消息事件，AES 解密 XML）→ 调用 `message/send` 主动推送。**免费**，无需企业认证也可注册试用（认证解锁更多 API 额度）。
- **双向收发**：✅ 完全双向（被动回复 + 主动推送 + 应用消息/群机器人 webhook）。
- **封号风险**：**极低（官方合规）**，是企业/团队自动化最稳路线。
- **服务化**：纯 HTTP 回调，天然适配任何后端（Docker/systemd/NSSM/pm2 均可）。
- 来源：企业微信开发者中心「回调配置」文档；CSDN《企业微信自建应用收发消息》等（≥2 个独立来源）。

#### 1.4 微信公众号测试号（官方，零门槛）

- **接入方式**：微信公众平台测试号（`mp.weixin.qq.com/debug/cgi-bin/sandbox`）扫码即可获得 appID/appsecret，无需企业资质，可测全量公众号接口（自定义菜单、客服消息、模板消息等）。
- **双向收发**：✅ 双向，但有限制——被动回复（用户发消息 5s 内回复）+ 客服消息（用户交互后 **48 小时窗口**内可主动推 1–N 条）。
- **封号风险**：极低（官方测试号）。
- **局限**：测试号是「一个订阅号」形态，适合个人/验证场景；量产需认证服务号或转企业微信。
- 来源：微信开放文档「测试号」页 + 博客园/CSDN 多篇（≥2 来源）。

### ④ 组合链路：'微信通道 → 路由框架 → 本地 agent 执行器' 如何拼装

标准三层拓扑：

```
微信用户 ──消息──> [微信通道] ──回调/长轮询──> [路由/机器人框架] ──任务──> [本地 agent 执行器]
                                                      │                          │
                                                   LLM 后端                   操作电脑/浏览器
                                              (任意 OpenAI 兼容/本地)
```

关键衔接点：

1. **微信通道 → 路由框架**：合规通道（企业微信自建应用 / 公众号测试号 / openclaw-weixin）通过 Webhook 或长轮询把消息送进框架；框架（AstrBot/LangBot/CowAgent/OpenClaw）负责鉴权、会话、指令解析、LLM 调用、多平台适配。
2. **路由框架 → 执行器**：框架把「指令」交给执行器。两种方式：
   - **内置式**：OpenClaw / CowAgent 自身带工具（执行命令、读写文件、浏览器），无需第三层；
   - **外挂式**：框架通过 HTTP 调用自建的执行器服务（如 Open Interpreter `--server`、UFO 封装服务、UI-TARS CLI），执行器回报结果，框架回传到微信。
3. **服务化**：三层均可 Docker 化；Windows 端可用 NSSM 将执行器/框架包成 Windows 服务自启动，Linux 端 systemd。

## 结论与置信度

### 核心结论

1. **【高置信度】个人微信 hook/协议开源项目已系统性退场**。WeChatFerry（归档）、Gewechat（停服）、ntchat（删库）三者由 GitHub API 仓库状态 + README + 多个独立文章交叉证实；腾讯官方打击公告是直接诱因。**新项目不应再选这几位做通道。**

2. **【高置信度】合规的个人微信通道已出现且是首选**：腾讯官方 `Tencent/openclaw-weixin`（扫码 + 长轮询，非逆向），以及更传统的「企业微信自建应用 API」「公众号测试号」。企业微信自建应用是**最稳、无封号风险、双向收发**的路线；openclaw-weixin 是**个人号**场景的正路。

3. **【高置信度】一体化方案最优选是 OpenClaw**（388k★）：本地优先、平台无关（任意 LLM）、自带 Gateway + 电脑操作工具 + 多消息渠道（含微信官方插件），完美满足三条硬性筛选；其次 **CowAgent**（原 chatgpt-on-wechat，46k★）与 **AstrBot / LangBot**（作为更轻的纯路由框架 + 官方微信适配器）。

4. **【中高置信度】纯「AI 操作电脑执行器」大多无开箱 HTTP 服务形态**，需自行包装服务层；Open Interpreter 有历史 `--server`（端口 8000 /openai）但当前主推终端/MCP，服务化能力需按版本核验；UFO³、UI-TARS 需封装。

### 推荐组合架构（2–3 条）

**架构 A（个人号 + 一体化，最省事）**
```
手机微信 ──扫码登录──> openclaw-weixin 插件 ──长轮询──> OpenClaw Gateway（systemd/Docker 常驻）
                                                        └─ LLM(任意) + 工具(执行命令/浏览器/文件) + 飞书/TG 等其它通道
```
- 优点：一套 OpenClaw 覆盖「通道 + 路由 + 操作电脑」，无需拼三层；官方微信插件合规。
- 部署拓扑：一台常驻机器（Linux/Docker 或 Windows NSSM）跑 OpenClaw Gateway，插件扫码一次登录态持久化，其余通道按需开启。

**架构 B（合规企业路线 + 轻框架 + 专业执行器，最稳、可量产）**
```
用户 ──企业微信自建应用──> 回调(HTTP) ──> AstrBot / LangBot（Docker）──> HTTP ──> 本地执行器服务
                                                                                ├─ Open Interpreter --server (8000)
                                                                                ├─ 微软 UFO³ 封装服务（Windows 桌面操作）
                                                                                └─ UI-TARS CLI（通用视觉 GUI）
```
- 优点：企业微信官方 API 零封号风险、双向收发稳定；框架负责多平台 + LLM 解耦；执行器按任务类型替换。
- 部署拓扑：回调服务需公网可达（内网穿透/云主机），框架与执行器同机或内网互联；执行器用 NSSM/Docker 常驻。

**架构 C（个人号想保留 + 轻框架）**
```
用户 ──WeChatPadPro(Docker, Pad协议)──> HTTP API ──> AstrBot ──> LLM + 自建执行器
```
- 优点：保留个人号、Docker 化、社区活跃；缺点：Pad 协议属灰色，有风控，最新版赞助付费——**仅限测试/小号场景**。
